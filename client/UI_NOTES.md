# Frontend — заметки по реализации

SPA на React 18 + Vite + TypeScript (strict), без SSR. Данные — TanStack Query,
таблицы — TanStack Table, формы — React Hook Form + Zod, запросы — axios,
маршрутизация — react-router-dom.

Структура — Feature-Sliced Design:

```
src
├── app/        провайдеры, роутер, layout, глобальные стили
├── pages/      восемь экранов задания
├── widgets/    боковое меню
├── features/   формы, фильтры, авторизация
├── entities/   user, promocode, order, analytics (api + хуки)
└── shared/     i18n, api-клиент, форматирование, ui-kit
```

## Тексты интерфейса

Единственный словарь — `src/shared/i18n/ru.ts`. Компонент берёт строку по ключу
функцией `t()` из `src/shared/i18n/index.ts`; ключи типизированы, опечатка не
собирается. Подстановки пишутся как `{name}` и передаются вторым аргументом:
`t('table.range', { from, to, total })`.

Правило «один смысл — один ключ» соблюдается буквально: «Промокод» в заголовке
колонки заказов, в подписи поля применения и в тексте уведомления — это один
ключ `field.promocode`. Дата создания пользователя и момент создания заказа —
один ключ `field.createdAt`: значение одного смысла показывается одинаково.
Исключение сделано там, где смысл действительно разный:
`field.totalDiscountReceived` (скидок получено пользователем) и
`field.totalDiscountIssued` (скидок выдано по промокоду).

Машиночитаемые коды превращаются во фразы тем же словарём: `tErrorCode(code)`
ищет запись `error.code.<CODE>`. Так закрыты все девять кодов применения
промокода и остальные именованные коды. Ни код, ни HTTP-статус на экран не
попадают: если кода нет, `apiErrorText()` подбирает фразу по статусу
(`error.validation`, `error.unauthorized`, `error.storageUnavailable`…).

Проверить требование можно так — поиск любой русской фразы по `src` находит её
только в `shared/i18n/ru.ts`. Русский текст вне словаря встречается лишь в
комментариях к коду.

## Мост через задержку репликации

Таблицы читаются из ClickHouse, а мутации уходят в MongoDB, поэтому строка
появляется в списке с отставанием до двух секунд. Из двух допустимых способов
выбран **короткий опрос до появления записи** (не оптимистичное слияние):
результат на экране всегда приходит из хранилища, а не дорисовывается клиентом,
поэтому расхождения «показали одно, сохранили другое» быть не может.

Реализация — `src/shared/api/useSyncedMutation.ts`:

1. Мутация возвращает полный документ, из него берётся `mongoId` и `updatedAt`.
2. Затронутые списки инвалидируются и перечитываются.
3. Если в перечитанных данных запись с этим `mongoId` уже есть и её `updatedAt`
   не старее мутации — опрос прекращается.
4. Иначе следует пауза и новая попытка. Расписание пауз —
   `SYNC_POLL_DELAYS_MS` в `src/shared/config/index.ts`
   (350, 500, 650, 900, 1200 мс — суммарно около 3,6 с при пяти попытках).
5. Пока опрос идёт, над таблицей видна полоса активности с подписью
   «Обновляем таблицу…».

Какие списки перечитывает какая мутация, задано в хуках сущностей. Например,
применение промокода трогает заказы, промокоды и все три витрины аналитики,
поэтому перечитывает их все (`src/entities/order/hooks.ts`).

Формы редактирования заполняются ответом `fetch/one` из MongoDB, а не строкой
загруженной таблицы: запросы `useUserDocument` и `usePromoCodeDocument` имеют
`staleTime: 0` и открываются вместе с модальным окном.

## Фильтр дат и параметры адреса

Фильтр общий для трёх аналитических экранов
(`src/features/date-range-filter`), границы считает клиент
(`src/shared/lib/dateRange.ts`) по местной полуночи браузера и отправляет в
нулевом смещении. Диапазон полуинтервальный `[dateFrom, dateTo)`.

При первом открытии пресет не выбран, границ нет, видны все записи.

Ключи в адресе страницы:

| Ключ | Значение |
| --- | --- |
| `period` | `today` \| `last7` \| `last30` \| `custom`; отсутствует — фильтра нет |
| `from` | нижняя граница произвольного диапазона, календарный день `YYYY-MM-DD` |
| `to` | верхняя граница **включительно**, календарный день `YYYY-MM-DD` |

Верхний день пользователь выбирает включительно, а на сервер уходит полночь
следующих суток — так «01.07 – 31.07» означает весь июль. Пример для UTC+3:
пресет «Сегодня» утром 30 июля даёт `dateFrom=2026-07-29T21:00:00.000Z`,
`dateTo=2026-07-30T21:00:00.000Z`.

Начало позже окончания на сервер не уходит: запрос отключается, под фильтром
появляется пояснение.

Состояние таблиц тоже живёт в адресе (`src/shared/lib/useTableUrlState.ts`),
общие ключи для всех восьми экранов:

| Ключ | Значение |
| --- | --- |
| `page` | номер страницы с единицы; отсутствует — первая |
| `size` | размер страницы, 1…100; отсутствует — 20 |
| `sort` | поле сортировки; отсутствует — поле по умолчанию экрана |
| `dir` | `asc` \| `desc`; отсутствует — направление по умолчанию |
| `q` | строка поиска |
| `active` | фильтр статуса пользователя на `/users` |
| `state` | фильтр состояния промокода на `/promocodes` и `/analytics/promocodes` |
| `promo` | фильтр `hasPromocode` на `/orders` |

Значения проверяются при чтении: в тело запроса к хранилищу произвольная строка
из адреса не попадает, недопустимое значение заменяется значением по умолчанию.

## Состояния данных

У каждой таблицы четыре различимых состояния — загрузка, пусто, ошибка, данные
(`src/shared/ui/DataTable`). Ошибка показывается текстом и кнопкой повтора
вместо таблицы: пустой выдачи и нулей при неудачной загрузке не бывает.

Показ ошибки укладывается в 10 секунд: таймаут запроса 4500 мс, одна повторная
попытка через 300 мс (`REQUEST_TIMEOUT_MS`, `QUERY_RETRY_COUNT`,
`QUERY_RETRY_DELAY_MS` в `src/shared/config/index.ts`). Кнопка повтора
перечитывает данные без перезагрузки страницы.

Ошибки мутаций доводятся уведомлением, ошибки полей из ответа `400` ставятся
рядом со своими полями (`src/shared/lib/serverFieldErrors.ts`).

## Авторизация

Пара токенов лежит в `localStorage` (`src/shared/api/tokenStorage.ts`), доступ
идёт заголовком `Authorization: Bearer`. На `401` перехватчик один раз меняет
refresh-токен на новую пару и повторяет запрос; обмен единственный на все ждущие
запросы, потому что refresh-токен одноразовый. Неудача обмена и код
`USER_DISABLED` немедленно очищают сессию и возвращают на вход. Целевой адрес
защищённого маршрута сохраняется в параметре `next`.

## Формы и телефон

Клиент повторяет серверные правила полей на Zod. Телефон разбирается той же
библиотекой, что и на сервере — `libphonenumber-js/mobile` со страной `RU` и
параметром `extract: false` (`src/shared/lib/phone.ts`), поэтому стационарный
`+7 495 …`, казахстанский `+7 701 …` и номер внутри фразы отвергаются одинаково
на обеих сторонах. Нормализует значение сервер: клиент отправляет ввод как есть.

Ошибки полей появляются по потере фокуса и обновляются по вводу, кнопка отправки
заблокирована, пока форма невалидна.

## Форматирование значений

Всё в `src/shared/lib/format.ts`, поэтому одинаково на всех экранах:
момент времени — `DD.MM.YYYY HH:mm` в поясе браузера без зоны, деньги — два
знака и `₽`, телефон — `+7 999 123 45 67`, пустая дата — `—`, промокод без
`validUntil` — «бессрочно», без `validFrom` — «с момента создания».

## Принятые решения

- **Колонка действий.** Состав колонок с данными закрыт заданием и соблюдён
  буквально. Кнопки строки («Изменить», «Деактивировать», «Применить») вынесены
  в отдельную колонку без заголовка: без них требование «всё делается из
  интерфейса» не выполняется, а данными эта колонка не является.
- **Активация.** Задание называет деактивацию и парную ей активацию, поэтому в
  интерфейсе есть обе: иначе деактивированную запись нельзя вернуть.
- **Регистрация с автоматическим входом.** `POST /auth/register` токенов не
  возвращает, поэтому сразу после регистрации выполняется `POST /auth/login` с
  теми же данными — пользователь попадает в систему одним действием.
- **Опрос вместо оптимистичного слияния** — обоснование выше.
